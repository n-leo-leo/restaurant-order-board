# Контракты адаптеров

Раздел задает требуемые сообщения на границе приложения. Это проектируемые контракты адаптеров, а не подтвержденные API банка, склада, кассы или комплекса. Пути REST, SDK, форматы подписей и допустимые интервалы вызовов определяются после получения спецификаций. Возможности A-02/A-03/A-05/A-08/A-14 остаются допущениями. Реестр систем и критерии подтверждения приведены в [интеграциях](../04_architecture/integrations.md).

## Общая оболочка и надежность

Команда содержит `operationId` (постоянный UUID), `restaurantId`, `purchaseId`, `correlationId`, `createdAt` и полезные данные. Для нефинансового обмена без покупки purchaseId отсутствует. Ответ содержит исходный operationId, внешний ID, состояние `pending / confirmed / rejected / unknown`, время наблюдения и версию состояния владельца. Событие дополнительно содержит `sourceId`, уникальный `eventId` и номер последовательности. Идентификаторы поставщика — непрозрачные строки. Суммы — копейки RUB, время — с часовым поясом. Точное количество ингредиента передается десятичной строкой с единицей, без двоичного float.

Прием включает проверку подлинности источника, ресторана, ID операции, связей и версии. Для денежных событий сверяются сумма и валюта. Несовпадение не запускает кухню и создает проблему. Дубликат подтверждается без повторного эффекта. Пропуск версии или противоречивое конечное состояние требует запроса фактического состояния владельца. Недоступный владелец оставляет операцию неизвестной. Поздний ответ не откатывает конечное состояние.

Команда и задание доставки сохраняются вместе с бизнесовым изменением. Обработчик повторяет исходную команду, не выделяет новый ID из-за сетевого сбоя. Для запроса состояния используется исходный ID. Необработанные задания и ключи дедупликации хранятся до определенного результата и не очищаются как технический журнал. Подтверждение клиенту дается после надежной записи. Параметры повторов согласуются с поставщиком; платежная сверка каждые 10 с обязательна по НФТ-10.

| I-01 Проверить пригодность | исходный reservationId и снимок заказа | fit/unfit/unknown, момент проверки и версия | Только fit разрешает кухню. Для подтвержденного пригодного резерва проверка и первая отправка в пределах 1 с от подтверждения оплаты. unfit и невозможность выполнения — проблема/полный возврат |
| I-02 Начать оплату | attemptId, purchaseId, reservationId, сумма, RUB, терминал | исходная попытка, внешний ID, processing/succeeded/declined/unknown | Потеря ответа — запрос attemptId каждые 10 с; через 1 мин менеджер. Карточные реквизиты в приложение не передаются |
| I-02 Полный возврат / проверка | refundId, исходный attemptId и внешний платеж, полная денежная сумма, причина | внешний ID, результат денег и момент подтверждения | MVP стартует снаружи; приложение сверяет зарегистрированный ID. R1 вызывает команду. Неизвестный исход не разрешает второй возврат |
| I-03 Исходное задание | jobId, purchaseId, снимок блюд/количеств, версии техкарт, тип обслуживания, reservationId | тот же jobId, принятие, этап приготовления, версия | Потеря ответа — запрос jobId; повтор доставки того же задания не повторяет приготовление. Кухня не ждет печати |

| I-03 Применить срок доступа | operationId, assignmentId, версия, защищенная ссылка/код талона, firstReadyAt, expiresAt | подтвержденные исходные assignmentId, версия и expiresAt, accessApplied=true | Только после подтверждения разрешается доступ; unknown — запрос применения исходного срока. Локальный запрет по expiresAt обязателен и без связи |
| I-03 Проверка талона и выдача | защищенный код, назначение и версия; события открытия/закрытия/контроля | действительный талон → открытие → закрытие → исправная стабильная пустота до срока | Частичный остаток сохраняет ready и срок. Неисправность скрывает номер и блокирует ячейку. Событие уборки не является выдачей |
| I-04 Продажа/возврат, чтение | fiscalOperationId, purchaseId, refundId для возврата, позиции и скидки, сумма, RUB, способ | внешний ID, результат формирования и ссылка на документ | Повтор исходного ID не создает второй расчет. Неизвестный исход — сверка, не новый платеж. Касса отвечает за ОФД |
| I-05 Печать, чтение | printTaskId, printerDeviceId, ссылки на чек и/или защищенный талон | результат printed/failed/unknown по исходной задаче | Тайм-аут не доказывает отсутствие бумаги. Менеджер после проверки может напечатать копию того же талона. Новый printTaskId для разрешенной копии не создает новый fiscalOperationId |

Первый показ подтверждается клиентским API; порядок установки срока и восстановления — в [правилах табло](resources.md#board) и [схеме готовности](../04_architecture/integration-flows.md#pickup).
После истечения срока комплекс запрещает новые открытия, даже если дверца уже открыта. Приложение не закрывает ее принудительно. Неоднозначный цикл передается менеджеру. Ячейка свободна только после безопасного закрытия, исправного стабильного контроля пустоты и завершенного обслуживания. Ручное обнуление выполняется в обслуживании после проверки физической пустоты по регламенту комплекса; удаление еды само по себе не восстанавливает датчик.

## Внутренние команды

C-02 получает серверный расчет от C-01, резерв от C-03 и результат платежа от C-04. При успехе одной транзакцией сохраняются оплата, номер, исходное задание C-05, задачи C-06 и доставка. C-05 создает версионную проекцию табло и хранит назначение/срок. C-07 принимает проблему, но не подменяет внешние факты. C-08 упорядочивает остановку продаж и регистрацию платежа по ресторану и поддерживает аудит.

Межмодульные вызовы не обязаны быть REST. Общая БД не дает клиенту или другому модулю права менять чужое состояние напрямую. Проверяемые ограничения сохраняются в командах владельцев данных и транзакциях.

# Контракты адаптеров

Требуемые сообщения приложения и внешних систем. API поставщиков еще не подтверждены; возможности A-02/A-03/A-05/A-08/A-14 остаются допущениями. Пути REST, SDK, подписи и интервалы вызовов уточняются по спецификациям поставщиков. [Реестр интеграций и условия подтверждения](../04_architecture/integrations.md).

## Общая оболочка и надежность

Команда содержит `operationId` (постоянный UUID), `restaurantId`, `purchaseId`, `correlationId`, `createdAt` и полезные данные. Для нефинансового обмена без покупки purchaseId отсутствует. Ответ содержит исходный operationId, внешний ID, состояние `pending / confirmed / rejected / unknown`, время наблюдения и версию состояния владельца. Событие дополнительно содержит `sourceId`, уникальный `eventId` и номер последовательности. Идентификаторы поставщика — непрозрачные строки. Суммы — копейки RUB, время — с часовым поясом. Точное количество ингредиента передается десятичной строкой с единицей, без двоичного float.

Проверяются подлинность источника, ресторан, ID, связи и версия; для денег — сумма и валюта. Несовпадение создает проблему и блокирует кухню. Дубликат подтверждается без нового эффекта. Пропуск версии или противоречие сверяются с владельцем; при его недоступности исход остается неизвестным. Поздний ответ не откатывает конечное состояние.

Команда, доставка и бизнесовое изменение сохраняются вместе, до подтверждения клиенту. Повтор и сверка используют исходный ID. Незавершенные задания и ключи защиты от дублей не очищаются с техническим журналом. Интервалы повторов согласуются с поставщиком; сверка оплаты каждые 10 с обязательна по НФТ-10.

## Сообщения MVP

|---|---|---|---|

| I-01 Создать резерв | reservationId, снимок состава/количеств и версий техкарт, срок до платежа | атомарный результат всего состава, внешний ID, expiresBeforePaymentAt, fitness и годность под ожидаемое приготовление | unknown — запрос того же reservationId; независимый дубль запрещен. До платежа 5 мин |
| I-01 Удержать/закрепить/освободить | исходный reservationId, attemptId, вид изменения | состояние исходного резерва и версия | Склад атомарно сравнивает свой срок и состояние: только до expiresBeforePaymentAt действующий резерв переходит в held для attemptId. Если действующий резерв не был удержан до срока, результат — expired. Повтор по тем же ID возвращает сохраненный результат удержания и после срока. Удержание отменяет автоматическое освобождение по пятиминутному таймеру. Ответ unknown сверяется до обращения к банку. Подтвержденное удержание сохраняется при неизвестной оплате. Отказ освобождает; новая попытка получает новый резерв |
| I-01 Проверить пригодность | исходный reservationId и снимок заказа | fit/unfit/unknown, момент проверки и версия | Только fit разрешает кухню. Для подтвержденного пригодного резерва проверка и первая отправка в пределах 1 с от подтверждения оплаты. unfit и невозможность выполнения — проблема/полный возврат |

| I-02 Полный возврат / проверка | refundId, исходный attemptId и внешний платеж, полная денежная сумма, причина | внешний ID, результат денег и момент подтверждения | MVP стартует снаружи; приложение сверяет зарегистрированный ID. R1 вызывает команду. Неизвестный исход не разрешает второй возврат |
| I-03 Исходное задание | jobId, purchaseId, снимок блюд/количеств, версии техкарт, тип обслуживания, reservationId | тот же jobId, принятие, этап приготовления, версия | Потеря ответа — запрос jobId; повтор доставки того же задания не повторяет приготовление. В R1 снимок комплектации содержит зарезервированный GiftAllocation (стакан, 1 шт.) при наличии подарка. Комплекс комплектует его один раз по jobId и возвращает результат комплектации. Кухня не ждет печати |
| I-03 Запрет дальнейших действий | исходный jobId, assignmentId при наличии, версия назначения, причина | подтверждение запрета новых приготовлений/открытий; фактический этап безопасной операции | Запрет должен сохраняться и при запоздалом приходе исходного задания. unknown — сверка, не обещание физической остановки |
| I-03 Размещение и контроль | события по jobId и assignmentId, cellId, версия, doorClosed, sensorHealthy, изменение веса и стабильность | подтвержденная порция в исправной ячейке; порядок событий восстанавливается | Окончание приготовления без размещения не разрешает выдачу. Нет ячейки/неизвестный контроль — проблема |
| I-03 Применить срок доступа | operationId, assignmentId, версия, защищенная ссылка/код талона, firstReadyAt, expiresAt | исходные assignmentId, версия и expiresAt, accessApplied=true; при сверке — интервалы фактического доступа с началом, концом, причиной блокировки, последовательностью и погрешностью времени | Только после подтверждения разрешается доступ; unknown — запрос применения исходного срока. Локальный запрет по expiresAt обязателен и без связи |
| I-03 Проверка талона и выдача | защищенный код, назначение и версия; события открытия/закрытия/контроля | действительный талон → открытие → закрытие → исправная стабильная пустота до срока | Частичный остаток сохраняет ready и срок. Неисправность скрывает номер и блокирует ячейку. Событие уборки не является выдачей |
| I-04 Продажа/возврат, чтение | fiscalOperationId, purchaseId, refundId для возврата, позиции и скидки, сумма, RUB, способ | внешний ID, результат формирования и ссылка на документ | Повтор исходного ID не создает второй расчет. Неизвестный исход — сверка, не новый платеж. Касса отвечает за ОФД |
| I-05 Печать, чтение | printTaskId, printerDeviceId, ссылки на чек и/или защищенный талон | результат printed/failed/unknown по исходной задаче; для талона — dispensedAt и погрешность часов при подтвержденном выходе бумаги в лоток гостя | Принятие задания и внутренняя печать не доказывают выдачу талона. Без подтверждения выхода бумаги исход для неявки неизвестен. Менеджер после проверки может напечатать копию того же талона. Новый printTaskId для разрешенной копии не создает новый fiscalOperationId |

Первый показ подтверждается клиентским API; порядок установки срока и восстановления — в [правилах табло](resources.md#board) и [схеме готовности](../04_architecture/integration-flows.md#pickup).
После истечения срока комплекс запрещает новые открытия, даже если дверца уже открыта. Приложение не закрывает ее принудительно. Неоднозначный цикл передается менеджеру. При сверке по assignmentId комплекс возвращает фактические моменты включения и блокировки доступа и последовательность событий с моментом завершения цикла. Подтвержденная выдача до expiresAt сохраняется. Интервал проверяется вместе с показом и выдачей талона по [условиям неявки](../03_model/order-states.md#pickup-window). Сокращенное окно и нерешенная проблема талона исключают автоматическую неявку. При невозможности исполнения действует A-12. Ячейка свободна только после безопасного закрытия, исправного стабильного контроля пустоты и завершенного обслуживания. Ручное обнуление выполняется в обслуживании после проверки физической пустоты по регламенту комплекса; удаление еды само по себе не восстанавливает датчик.

В R1 отмена по просьбе гостя использует условную команду I-03 по jobId и постоянному ID запроса. Комплекс атомарно упорядочивает начало приготовления и запрет. Если первым принят запрет, результат stopped_before_start сохраняется даже при последующей доставке задания. Если приготовление уже началось, возвращается already_started, выполнение продолжается. При тайм-ауте проверяется тот же ID.

## Внутренние команды

C-02 получает серверный расчет от C-01, резерв от C-03 и результат платежа от C-04. При успехе одной транзакцией сохраняются оплата, номер, исходное задание C-05, задачи C-06 и доставка. C-05 создает версионную проекцию табло и хранит назначение/срок. C-07 принимает проблему, но не подменяет внешние факты. C-08 упорядочивает остановку продаж и регистрацию платежа по ресторану и поддерживает аудит.

Межмодульные вызовы не обязаны быть REST. Общая БД не дает клиенту или другому модулю права менять чужое состояние напрямую. Проверяемые ограничения сохраняются в командах владельцев данных и транзакциях.

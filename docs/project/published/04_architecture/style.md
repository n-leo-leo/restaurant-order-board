# Архитектурный стиль

Для MVP выбран модульный монолит с реляционной БД и адаптерами внешних систем. Киоск, табло, минимальный экран сотрудника и локальный адаптер оборудования развертываются отдельно от серверного приложения. Монолит относится к бизнес-логике, а не к размещению всей системы в одном процессе.

## Сравнение вариантов

| Критерий | Модульный монолит | Микросервисы |
|---|---|---|
| Согласованность заказа и оплаты | Снимок, результат и задание сохраняются одной транзакцией | Требуются согласование нескольких хранилищ и восстановление промежуточных результатов |
| Нагрузка | Масштабирование экземпляров приложения; расчетный пик сети 7,22 заказа/с до учета остальных операций | Независимое масштабирование полезно при доказанном различии нагрузок, которого пока нет |
| Отказ внешнего контура | Изолированные адаптеры, лимиты времени и числа одновременных вызовов | Изоляция процессов лучше, но добавляются сетевые отказы внутри приложения |
| Эксплуатация | Меньше развертываемых компонентов и хранилищ | Нужны отдельные развертывания, наблюдаемость и согласованные версии контрактов |
| Развитие | Модули и владельцы данных задаются заранее | Сервисы можно выделять по установленным границам |

Модульный монолит позволяет сохранить согласованность покупки, оплаты и задания кухне в одной БД. Взаимодействие с внешними системами выполняется через адаптеры. Для MVP используются общая БД и сохраненные задания без отдельного брокера сообщений и аналитического хранилища.

## Правила реализации

Каждый модуль изменяет только принадлежащие ему таблицы. Взаимодействие проходит через внутренние интерфейсы. Одна БД позволяет атомарно сохранить подтвержденную оплату и задание кухне. Внешние вызовы не удерживают длительную транзакцию БД: до вызова сохраняется намерение, после — подтвержденный результат.

Задача отправки записывается вместе с бизнес-изменением (transactional outbox). Рабочий процесс берет задачу с ограниченной по времени блокировкой, отправляет ее и сохраняет результат. После сбоя обработка задачи возобновляется с прежним ID. Входящие события проверяются на повтор и порядок. Это доставка с возможными повторами; однократное приготовление требует защиты также на стороне комплекса.

Ожидание эквайринга, кассы и склада не блокирует обработку других заказов. Для каждого адаптера задаются отдельные очереди, ограничения параллельности и тайм-ауты. Неизвестный исход не превращается в отказ. Необработанная задача не исчезает после трех попыток: проблема передается менеджеру, сверка продолжается.

REST по HTTPS применяется на границах приложения. События могут поступать входящим REST-вызовом или через опрос REST состояния. Наличие таких интерфейсов у конкретного оборудования подлежит проверке. Для клиентского обновления выбран REST-опрос с версиями, без обязательного WebSocket. Период опроса и число табло учтены в расчете нагрузки.

## Когда пересматривать стиль

Выделение сервиса рассматривается, если измерения покажут отдельное узкое место, необходимость независимого выпуска или отказа модуля, либо появятся независимые команды сопровождения. При росте до 130 ресторанов проверяется достаточность выбранной архитектуры по расчетному профилю нагрузки. Доступность при резервировании проверяется по НФТ-04, восстановление после сбоя — по НФТ-06.

# Решения и допущения

Решения, принятые при подготовке проекта, и их обоснование.

| № | Решение | Обоснование | Статус |
|---|---|---|---|
| 1 | MVP = приложение для заказа в киоске + табло выдачи заказа. Мобильное приложение в MVP не входит | Противоречие в протоколах: Product Owner — мобильное приложение (протокол 1, №12), CTO — мобильное приложение не входит в MVP (протокол 3, №16). Макеты и архитектура выполнены под киоск | Согласовано с преподавателем 09.11.2026 |
| 2 | Конструктор комбобургера в MVP не включаем. Комбо-наборы из готовых блюд остаются | Ограничение технолога: на текущем этапе клиент не может менять конфигурацию блюда (протокол 2, №10) | Согласовано с преподавателем 09.11.2026 |
| 3 | Требования описываются через User Story. Диаграмма Use Case — обзорная схема | Достаточно одного формата представления требований | Согласовано с преподавателем 09.11.2026 |
| 4 | Ожидаемая нагрузка берется из прогноза ДЗ 13 (около 400 заказов в день на ресторан). Значения протокола 1 (2000 заказов в сутки, 200 в час) — требование к пропускной способности одного ресторана | Прогноз и требование не противоречат: прогноз ниже требования в 5 раз, это запас производительности | Принято |
| 5 | Время оформления заказа в киоске — не более 3 мин (медиана) | В протоколе 1 значение не зафиксировано (открытый вопрос №3) | Принято |
| 6 | Если основной и резервный робот недоступны, заказ получает статус «Проблема», менеджер гостеприимства получает уведомление, гостю на табло показывается «Обратитесь к менеджеру» | Альтернативный поток не описан (протокол 2, открытый вопрос №4) | Принято |
| 7 | Выдача заказа автоматическая: робот помещает заказ в ячейку выдачи, гость открывает ячейку талоном, заказ получает статус «Выдан» | Ресторан автоматизированный, персонал на выдаче не нужен | Принято |
